# Lab Recipe test harness v0.2.0 — cross-surface extension — release

## TL;DR

v0.2.0 extends the v0.1.0 Recipe/Subscription test-harness pattern (ADR-0048) across 4 cross-surface waves so that every Lab/cockpit live subscription now has a default-FAIL boundary test plus a state/stream oracle — all 4 waves tester-PASS, anchor-additive zero (84/84 byte-stable), and every probe re-ran RED-on-mutation.

## What changed

- **Cross-surface coverage closed.** The two-surface harness that v0.1.0 proved on `spawn_lab_run` now covers seven more live recipes: TrainingLog, ActivityAuditAggregator, ServerTime, ToastDismiss, TrailMirror, Activity, and TrainingPoller. Every `impl Recipe` / Subscription in `crates/ui/` and `crates/agent/` now has at least one boundary or gating test.
- **Three small production seams added** to make the recipes testable, all API-additive (production behaviour unchanged): `run_aggregator_loop` (Wave B), `build_subscription_batch_descriptor` (Wave C — also unifies the live cockpit subscription with one introspectable descriptor), and `training_poller_stream_impl` (Wave D).
- **The harness is proven, not assumed.** Each of the 11 falsification probes was re-run by the tester with the one load-bearing line broken; each turned at least one test RED, then GREEN again on restore. This is the durable lesson from v0.1.0 made mechanical: a test that never fails is not a test.

## Why

v0.1.0 was created only after a 415-test-PASS gate set still let three live regressions reach the operator's visual-verify (Bug #64 attempt 1). v0.1.0 covered only the one recipe that broke; four other recipes plus three partially-covered ones had the exact same shape — an mpsc/broadcast channel plus an `Arc<Mutex<Option<_>>>::take()` plus a state-gated predicate, and zero boundary test. Rather than wait for the next visual-verify revert, the operator chose the durable option (Q1=(a) + Q2=(a)): apply the proven pattern PREEMPTIVELY to every vulnerable recipe now, with a per-recipe falsification proof, so the next regression in this class is caught at `cargo test` time. See [`feature.md`](../feature.md) § Why and § Operator decisions.

## What you can do now

These are developer/CI-facing capabilities — v0.2.0 is a test-harness feature with no new user-visible cockpit surface. The "actions enabled" are the regression gates the operator's CI and future feature work now inherit.

| Action | Command |
|--------|---------|
| Run the full v0.2.0 cross-surface harness (UI side) | `cargo test -p ui --no-default-features --features live` |
| Run one recipe's boundary test (example: TrailMirror gating) | `cargo test -p ui --test trail_mirror_subscription_handle_gating --no-default-features --features live` |
| Run the agent-side select-arm survival test | `cargo test -p agent --test activity_audit_aggregator_select_arm_survival` |
| Re-confirm byte-stable backtest output (anchor gate) | `bash scripts/verify_anchors.sh` |
| Reproduce a falsification probe (prove a test still bites) | Comment out the line named in the test's `## T-T4 falsification probe` docstring, re-run that test, expect RED, restore. |

## Cross-feature safety

The one structural risk in v0.2.0 was the Wave D extraction of `training_poller_stream_impl`, because the `TrainingPoller` recipe carries the **Bug #64 P1 fix** (`rt_handle.enter()` before constructing the `tokio::time::interval`, guard dropped immediately so the stream future stays `Send + 'static`). The tester read the refactored `Recipe::stream` (`training_subscription.rs:93-111`) and confirmed the `enter()` guard is still called synchronously before the ticker is built, then the pre-constructed ticker is passed into the extracted function — the fix is preserved (final report § 5, OQ-D3). The Bug #64 + lab-yahoo cross-feature suite (`lab_runner_preload_callthrough_e2e`, `lab_runner_cancel_e2e`, `lab_yahoo_empty_range_classification`) ran **7/7 PASS**.

## Open decisions

No decision is required to ship. Two follow-ups are surfaced for awareness only — both are documented, in-budget, and explicitly accepted by the tester. Ticking "Approved — ship" carries no follow-up cost.

1. **10ms-ticker vs `tokio::time::pause()` (non-blocking).** The Wave D `TrainingPoller` tests use a 10ms fast ticker rather than `tokio::time::pause()`, because pausing the clock makes sqlx's in-memory SQLite pool time out immediately ("pool timed out"). Wall-clock is ~40ms/test, well inside the 1.5s ADR-0048 D4 budget. The tester ruled this ACCEPTABLE and the test docstring documents the rationale (final report § 5 OQ-D1). If you ever want clock-virtualized poller tests, that is a v0.3.0 sqlx-pool-shim question, not a blocker here.
2. **~10 pre-existing `crates/ui` pedantic clippy warnings (carry-forward).** These sit on untouched functions (e.g. `runner.rs` unused-import/unused-variable, `live.rs` `#[must_use]` suggestions) and predate v0.2.0; the harness added zero new ones. Tracked as standing debt in [`spec/dev-notes/audit-2026-05-29.md`](../../dev-notes/audit-2026-05-29.md); not part of this feature's scope.
