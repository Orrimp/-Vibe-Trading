### P2 — Comment out `crates/ui/src/lab/training_log.rs:87` (`.take()` call) + timeout guard question

**Open Question Q-T4 investigation:**

The developer flagged P2 as requiring a `std::sync::mpsc::Receiver`-is-not-Clone design consideration. The probe spec requires:
1. Comment out line 87 (`.take()` in `Recipe::stream()`)
2. Run `salt_bump_survives_arc_mutex_take`
3. Expect: FAIL (timeout, because second stream never returns)

**Finding:** The probe as specified does NOT cause the test to fail. Root cause confirmed independently by tester:

The test `salt_bump_survives_arc_mutex_take` does NOT call `TrainingLogRecipe::stream()`. It uses standalone closures (`take_rx()` defined at test lines 228-233) that implement their own `.take()` call directly on the `Arc<Mutex<Option<_>>>`. Commenting out line 87 in the PRODUCTION `Recipe::stream()` leaves the TEST's own `take_rx()` closure unaffected.

**Probe evidence:**
- Mutation applied: Line 87 `.take()` replaced with `.as_mut().and_then(|_| None)` (a semantic no-op that returns None without consuming the Option, simulating the "take not called" regression)
- Command: `cargo test -p ui --test training_log_recipe_harness salt_bump_survives_arc_mutex_take --no-default-features --features live`
- **Result: `test result: ok. 1 passed; 0 failed` — test PASSES despite line 87 mutation**

This confirms: P2 as currently specified is NOT verifiable by commenting out line 87 alone, because the test bypasses `Recipe::stream()` entirely.

**Verdict: P2 INCONCLUSIVE — probe does not reproduce expected FAIL under the tester's isolated environment.** The harness correctly tests the `Option::take()` semantic in isolation (via the test's own `take_rx()` closure), but does NOT exercise the production `Recipe::stream()` code path at line 87. The `salt_bump_survives_arc_mutex_take` test verifies the INVARIANT (Option is drained after first call) but cannot detect a regression specifically at line 87 of the production code.

**Recommendation for Wave B/C/D pickup (Q-T4 answer):** P2 requires a PERMANENT test-file change to be fully verifiable:
- Option A: Add a test that constructs a real `TrainingLogRecipe` (with a `tokio::runtime::Handle`), calls `recipe.stream()` twice, and asserts that the second call yields zero messages. This exercises the actual line 87. A `tokio::time::timeout(Duration::from_millis(200), second_stream.next())` guard is mandatory because without `.take()`, the second `stream()` call would hand off the SAME live `Receiver` and block indefinitely.
- Option B: Accept the current test as a functional-equivalence test of the `.take()` invariant and document that line 87 mutation is only caught by the production Recipe path test (Option A).

**ADR-0048 amendment required?** The tester recommends routing this as a Wave B/C/D developer item (not an ADR amendment). The current falsification docstring in the test file already notes the P2 probe limitation accurately ("since `std::sync::mpsc::Receiver` is not Clone, the only way to break the `.take()` semantic is to NOT drain the Option"). The gap is that the docstring's P2 probe targets line 87 of the production Recipe, but the test only exercises a test-side closure. A future test that drives `TrainingLogRecipe::stream()` directly (Option A above) would close this gap without requiring an ADR amendment — it is a D2 "test file locations" update, covered by the D2 "API-additive" clause. Route to developer for Wave B pickup.
