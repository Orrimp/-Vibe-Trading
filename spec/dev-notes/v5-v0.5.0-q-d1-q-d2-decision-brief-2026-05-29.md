### Cost framing — both routes

- **Q-D1=(a) Linear fallback (Recommended — DURABLE)** —
  ~0.5 dev-day NOW + ZERO v0.6.0 follow-on. The 9 synthetic SHAs
  stay byte-identical to `v5-realdata-medium-2026-05` linear-bps
  twins; the t1937c resolver was designed to handle exactly this
  case (the Q-D1=(a) namespace contract). No v0.6.0 sub-namespace
  split commitment to retire. **Net: ~0.5 dev-day total cost.**
- **Q-D1=(b) SquareRoot + universe-avg V on synthetic** —
  ~1 dev-day NOW + ~2-3 dev-days v0.6.0 sub-namespace cleanup
  commitment recorded at architect M-T1 D-T1.5. Operator picked
  this at M-OD 2026-05-29 with "synthetic scenarios should behave
  more real-data-like for testing purposes" framing — BUT that
  framing was BEFORE we had evidence on what universe-avg V on
  synthetic actually accomplishes. The Q-D1=(b) value-prop now
  collapses: synthetic GBM Q × real-universe-avg V is a
  dimensionally-mixed comparison, not "behavior more real-data
  like." **Net: ~3-4 dev-days + ~2 cognitive context-swap cycles
  (v0.6.0 cleanup).**

### Frame both sides — what's the (a) cost?

The Q-D1=(a) honest downside: **synthetic scenarios become test-only
deterministic, not analytical**. The 9 SHAs cannot be used to
"validate the sqrt model on a controlled signal" because the sqrt
model does not run on synthetic data at all. If the operator's M-OD
intent was specifically "stress-test the sqrt model body on synthetic
inputs as a determinism oracle," Q-D1=(a) defeats that intent and
Q-D1=(b) is justified.

But: Wave A already shipped 14/14 unit tests on `apply_slippage_sqrt`
including α=1.0 → 316 bps reference, cap saturation, deterministic
edge cases, sell/buy symmetry. The "sqrt model determinism oracle"
function is **already covered at the unit-test layer** — running 9
synthetic backtests on top of unit tests adds ~zero unit-test signal
and only adds anchor-surface and v0.6.0 cleanup commitment.

### Q-D1 — Recommended (DURABLE)

**(a) Linear{bps:8} fallback for synthetic scenarios.**

Rationale: durable per the 2026-05-28 contract — the durable choice
is the one whose architect M-T1 lock carries forward across multiple
feature versions without amendment. Q-D1=(a) does not spawn a v0.6.0
sub-namespace cleanup brief; Q-D1=(b) explicitly commits to one. The
"more real-data-like synthetic behavior" Q-D1=(b) value-prop collapses
post-evidence — the dimensional mix of synthetic Q × real universe-avg
V produces a contaminated signal, not a cleaner one. Wave A unit tests
already cover the sqrt-model-body-on-controlled-input use-case.

### If-budget-tightens fallback

If the operator insists on the M-OD 2026-05-29 Q3=(b) ratification
(operator-locked decisions stay locked absent new evidence), Q-D1=(b)
is the fallback. In that case the +2-3 dev-day v0.6.0 sub-namespace
cleanup brief gets explicitly queued at v0.5.0 ship (not deferred to
v0.6.0 spawn time).

### Q-D2 — Recommended (DURABLE)

**(β) Per-scenario lazy-compute, cache via existing Wave C dashmap.**

Rationale: durable per the 2026-05-28 contract — (β) aligns verbatim
with the architect M-T1 D-T1.5 contract ("pinned to scenario's own
end_date"); (α) pre-compute violates that contract and adds v0.6.0
rework debt; (γ) CLI flag adds operator burden and a new SHA
provenance gap (operator-supplied values not captured in parquet
revision SHA). The dashmap cache already shipped in Wave C — no new
code, no new tests, no new operator burden.

### Frame both sides — what's the (β) cost?

The Q-D2=(β) honest downside: **cache miss → network call / parquet
read mid-scenario**. The first scenario in each end_date group
triggers a ~200ms cold parquet read. Total cold-path overhead is
~5-8 × 200ms = ~1-2 seconds across the 19-scenario sweep. Negligible
against the ~30-45 minute Wave D total.

If the operator wants the Wave D run to be "all I/O up-front, then
pure compute" (e.g. for tracing latency profiling), (α) is justified.
That's an unusual preference and the ~2-3 hr implementation cost +
v0.6.0 rework debt make it strictly worse for the v0.5.0 ship.

### If-budget-tightens fallback

Q-D2=(α) — pre-compute. Cheaper to reason about ("one fetch, N reads"
mental model). Violates the D-T1.5 end_date-pin contract but the
violation is a one-line architect amendment, not a re-arch.

## § Risks

### K1 — operator picks Q-D1=(b) and synthetic V proxy contaminates Sharpe-delta interpretation

If operator ratifies the M-OD 2026-05-29 Q3=(b) lock under Q-D1=(b):
the R5 Sharpe-delta table shows the sqrt-impact column for the 9
synthetic scenarios as a dimensionally-mixed signal (synthetic Q ÷
real universe-avg V). The "H1 directional check" (sqrt drag ≥ 2×
linear drag on high-turnover) becomes hard to interpret on synthetic
rows because the synthetic signal generator's Q magnitude has no
real-world correlate to "high-turnover." Tester M-FINAL must
explicitly exclude the 9 synthetic rows from H1/H2 verdict; this
narrows the directional signal to 10 real-data rows only. If those 10
rows agree directionally with H1, fine; if 4 of 10 disagree (mixed
signal), tester FAIL-defers to analyst for K1-surprise interpretation.

**Mitigation**: tester M-FINAL contract explicitly carves out
"synthetic rows excluded from H1/H2 hypothesis check" if Q-D1=(b)
is chosen. Already documented in `feature.md` § D-T1.5 SHA-divergence
acknowledgment.

### K2 — operator picks Q-D2=(γ) CLI flag and V drifts silently over time

If operator picks the CLI-flag-inject route: the operator-supplied V
becomes opaque to the parquet revision SHA gate. Future re-runs (e.g.
6 months out) might use a stale V value (operator forgot they
overrode it; the canonical revision-pinned V from Binance has drifted
~20-30% since). The Sharpe-delta interpretation becomes time-dependent
in a way the architect M-T1 D-T1.5 contract explicitly forbids.

**Mitigation**: if Q-D2=(γ) chosen, tester M-FINAL contract must record
the CLI-supplied V value in the report frontmatter under
`sim_slippage_sqrt_universe_avg_v_decimal_override: <value>` and emit
a warning log line at scenario start. v0.6.0 sub-namespace cleanup
brief queues a "retire-and-recompute under Q-D2=(β) lazy-compute"
commitment.

## § Hypotheses

### H1 — sqrt-vs-linear Sharpe-delta is observably > 0 bps for real-data scenarios under Q-D1=(a)

Hypothesis: when Q-D1=(a) restricts the sqrt model to the 10 real-data
scenarios only, the Sharpe-delta table column "sqrt-impact vs
linear-bps" shows ≥ 2× linear drag on TCN-realdata scenarios (per the
brief H1) and ≤ 30% delta on low-turnover scenarios (per H2). The
restricted sample (10 instead of 19) doesn't dilute the directional
signal because the 9 synthetic scenarios were never expected to
exhibit interesting sqrt-vs-linear behavior (synthetic Q magnitudes
are GBM-bounded, not market-flow-driven).

**Falsifier**: 4+ of 10 real-data scenarios show sqrt drag < 2× linear
drag → H1 directional fails → route to analyst for v0.5.1 α
calibration brief.
