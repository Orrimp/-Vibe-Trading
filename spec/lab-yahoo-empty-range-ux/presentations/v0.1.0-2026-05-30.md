# lab-yahoo-empty-range-ux v0.1.0 — Ship deck (release)

## TL;DR

A Yahoo fetch that finds **no data for the requested window** now shows a
muted, plain-language NOTICE ("no Yahoo data for this range") instead of a
misleading red error — the exact rough edge you hit during Bug #64
verification — and ships tester-PASS with **84/84 anchors, zero anchor
delta**.

## The behavior change that matters to you

This is the part you will actually see. Before and after, for the precise
scenario you ran during Bug #64 D.1.1 verify (cockpit Lab → Yahoo source →
`Last 30d`, which resolves to a future-dated window under the 2026 test
clock that Yahoo has no bars for):

| | Before (today's behavior) | After (this ship) |
|---|---|---|
| **What you see** | Red `⚠` error message | Muted `ⓘ` NOTICE in neutral text |
| **The text** | `⚠ Yahoo auto-fetch failed for SOL-USD: … Check network connectivity…` (referenced an internal `CacheMiss`/`MissingData` error) | `ⓘ No Yahoo data for SOL-USD in <window> — the range may be future-dated or the ticker may be delisted.` |
| **What it implied** | Something is **broken**; go check your network | This is an **expected** outcome; nothing is wrong |
| **Run state** | Looked like a failure | A **completed** run with zero bars — Run button is NOT in the Failed state, no stuck spinner |

The friction this fixes: you could not tell **"broken"** from **"there is
simply no data here."** The red "check network" hint actively pointed you
at the wrong cause. The muted notice now names the ticker and the resolved
date window so the future-dating — your primary confusion source — is
visible.

## What changed (file-level)

- **`crates/data/src/yahoo.rs`** — new `YahooError::NoDataForRange` variant,
  emitted **only** on an HTTP-200, well-formed response that returned zero
  quotes. Transport failures and HTTP-429 rate-limits still map to the
  existing `Http` / `RateLimited` errors — an outage is still an error.
- **`crates/ui/src/lab/runner.rs`** — a single classification chokepoint
  (`preload_notice` module), a non-retry early-out so a no-data window does
  not burn the 5×60s retry budget, and a future-date clamp
  (`end_ms.min(now_ms)`) in `range_to_ms_pair`.
- **`crates/ui/src/lab/state.rs`** — a new `last_run_notice` field, separate
  from `last_run_error`, so the muted notice and the red error never share
  state.
- **`crates/ui/src/screens/lab.rs`** — a muted `FG_2` notice render branch.
  The existing red `⚠` error branch is left **byte-identical** (no token
  work, no new design color).

## Why

During Bug #64 D.1.1 verification (2026-05-29) you repeatedly hit confusion
with the `Last 30d` / `Last 90d` Yahoo presets: under this environment's
future-dated 2026 clock those presets compute a window Yahoo has no bars
for, and the cockpit surfaced that empty result as a red error with a
"check network" hint — indistinguishable from a real outage. The Bug #64
attempt-3 deck explicitly carried this forward as FYI #2 (a candidate
UX-polish feature). This v0.1.0 discharges that carry-forward: it makes the
"no data" outcome read as the expected, non-alarming thing it is, while
leaving genuine fetch failures looking exactly as alarming as before. See
[`feature.md`](../feature.md) § Motivation and the
[Bug #64 attempt-3 deck](../../bug-64-d11-attempt-3-yahoo-run-runtime-context/presentations/bug-64-attempt-3-2026-05-29.md)
§ Notes/feedback FYI #2.

## The classification gate (the durable value)

The load-bearing engineering decision is that "no data" and "fetch error"
are **provably distinct outcomes**, not a guess from a bar count. The K2
required-gate test drives two cases through the same path and asserts they
route to **different surfaces**:

- empty source (HTTP-200, 0 quotes) → muted `last_run_notice`, no error;
- transport error (e.g. connection refused) → red `last_run_error`, no notice.

This is the K1 risk discharged: a Yahoo outage that returns 0 bars still
reads as an **error** (so you are prompted to retry), never as "no data."
The P-ER-1 falsifier confirmed the test is not vacuously green — removing
the routing sentinel flips the no-data case to the error surface and the
test FAILs as designed (developer dry-run + tester re-confirmed).

### Non-blocking follow-up (no action required to ship)

1. **Future-date boundary uses `now_utc()`, not a true last-available-bar
   probe.** The clamp treats "future-dated" as `end_ms > now`. Determining
   Yahoo's true last-available bar for a ticker needs a network call we
   deliberately keep off the render path (K4). A richer last-available-bar
   probe is **deferred to v0.2.0+** per the analyst (H3/K4) — pick it up only
   if the `now`-based boundary proves insufficient in practice. This is
   noted, not a gate.
