# Bug #64 — Lab → Yahoo → Run "endless spinning / can't stop" — release

## TL;DR

The Lab → Yahoo → Run bug where the screen span forever, showed no progress,
and ignored the Stop button is **CLOSED** — you already confirmed "it works",
and the durable fix plus its regression guard are now landed and tested at
commit `e72aca5`.

## What changed

- **The fetch now runs on the right engine.** The Yahoo download is handed to
  the background worker pool (`rt.spawn`) instead of being run on the UI's own
  thread, which had no working timer/network plumbing. That was the single
  cause behind all three "endless spinning" recurrences.
- **One enforcement point, not two.** Both the real Yahoo path and the test
  path now go through a single function (`spawn_preload_on_rt`). You cannot
  accidentally re-break one path without breaking the other — the compiler
  stops you.
- **Stop works during the download.** Pressing Stop while bars are fetching now
  cancels the in-flight request and returns the cockpit to idle in about a
  second. Previously you had to wait out the full 30–60 s fetch or force-quit.
- **The rule is written down for good.** A new architecture decision record
  (ADR-0050) codifies the iced↔tokio runtime-context contract so this class of
  bug has a durable home instead of living in a comment that got lost.

## Why

This bug had bitten the project three times (2026-05-23, attempt-2, and this
attempt-3), each time one layer deeper in the call stack. The cockpit's UI
framework (iced) runs background work on a thread pool that does NOT carry the
"tokio runtime context" — the bookkeeping that timers and network calls need to
function. Without it, a timer never fires (silent hang, no crash) and a network
DNS lookup panics. The previous fixes patched the symptom at each visible site;
the durable fix moves the whole download onto the worker pool that always has
that context, and writes the rule into ADR-0050 so it stops recurring. Full
rationale: `spec/bug-64-d11-attempt-3-yahoo-run-runtime-context/feature.md`
§ Root cause analysis + § Hotfix-2.

## The saga — three recurrences, each one layer deeper

This is the load-bearing story. Frame it honestly: the architect's mental model
of where the runtime context was needed was wrong **twice**, and each time it
was your real-world re-verify — not the test suite — that caught it. The
"developer code-maps the call graph, then architect + analyst validate it in
lockstep" approach you proposed is what finally cracked it.

1. **Recurrence #1 — the progress label (`runner.rs:744`).** A 250 ms ticker
   (`tokio::time::interval`) was constructed on the UI thread with no runtime
   context, so it silently never fired — label stuck at `0/1 · 0.0s`. Fixed
   with an `rt.enter()` guard around the timer construction. Tester PASS at
   commit `a87b5fa` (report `test-20260529-181500-v0.1.0.md`).

2. **Recurrence #2 — the fetch timeout (`runner.rs:395`).** You hit a NEW panic
   on a cold-cache re-verify: `there is no reactor running`. The architect's
   earlier assertion that "reqwest carries its own reactor, so the timeout
   doesn't need a guard" was **FALSIFIED** by your re-verify. The hotfix added
   guards to the `tokio::time::timeout`/`sleep` calls in `fetch_with_backoff`.

3. **Recurrence #3 — the DNS resolver (`hyper-util .../dns.rs:119`).** You hit
   the SAME panic AGAIN — but now one level deeper, inside reqwest's own DNS
   lookup, which calls `spawn_blocking` lazily long after the guard had been
   dropped. The architect re-validation
   (`bug-64-arch-revalidation-rt-spawn-2026-05-29.md`) owned the falsified
   assertion, derived the mechanism from tokio source, and landed the **durable
   fix**: stop trying to guard individual call sites and instead `rt.spawn()`
   the entire download onto the worker pool, where the context is always
   present. Cancel was upgraded too — `fetch_join.abort()` actually stops the
   request rather than just detaching it.

The honest takeaway: guards at each visible site were correct-but-incomplete
twice. The spawn-the-whole-thing fix is correct-by-construction because a task
spawned onto the worker pool always carries the context, no matter how deep the
call graph goes.

## The regression-guard story — why the tester pushed back twice

The fix worked, but the tester refused to PASS it until the *guard* was real.
This is the durable-over-quick discipline doing its job, and it is worth seeing:

- **INCONCLUSIVE** (`test-20260529-184016-rt-spawn.md`). The first rt.spawn fix
  shipped with an HTTP-mechanism test, but that test exercised the broken
  primitive in isolation — it never called through production `runner.rs`.
  Reverting the real fix would NOT have failed any test. Test theater. Routed
  back to developer.
- **CHANGES-REQUESTED** (`test-20260529-201208-callthrough.md`). The developer
  added a call-through helper (`spawn_preload_on_rt`) and routed the mock path
  through it — but the *production* Yahoo path still had its own separate
  `rt.spawn`, so a revert of the production site alone could slip past. Worse,
  the helper's doc comment *claimed* both paths routed through it, which was
  false. The tester demanded unification (Option B), citing exactly the
  durable-over-quick contract and the Bug #64 recurrence history.
- **PASS** (`test-20260529-202732-unify.md`). The developer unified both paths
  through `spawn_preload_on_rt` — now the single enforcement point. The tester
  proved it mechanically: adding a dummy parameter to that function breaks
  **both** call sites at compile time simultaneously (§ 3 Gate 4). That is the
  durable close — you cannot re-introduce recurrence #4 without the build
  failing.
