### Gate 2 — RED-on-mutation (solvency guards)

**PARTIAL — arithmetic proof valid; run_path call path not covered by either solvency test.**

Finding: Both solvency tests were GREEN under the mutation (solvency guard reverted to Bug B code in montecarlo.rs):

1. `solvency_guard_arithmetic_unit_test` — does NOT call `run_path`. It is a self-contained pure arithmetic test that encodes the fix logic inline and computes `cash_after_old_bug < 0`. It proves the **arithmetic invariant** correctly and stays GREEN under mutation because it does not invoke the production code path. This is intentional design — the test proves the math, not the code path.

2. `solvency_invariant_equity_curve_never_negative_across_paths` — uses `fake_equity_curve` (a price-ratio tracker, no trading), so it also does NOT exercise `run_path`. GREEN under mutation for the same reason.

3. The comment in `montecarlo_e2e.rs:438-439` references a unit test `solvency_guard_prevents_negative_cash` in `montecarlo.rs` that **does not exist**. This is a dangling comment — the referenced test was not implemented.

**Impact assessment:** The mutation probe does not find a test that calls `run_path` and goes RED when the guard is removed. The solvency tests are genuine guards for the arithmetic invariant, but they do not provide end-to-end RED-on-removal for the `run_path` code path.

**What is protected:** The `solvency_guard_arithmetic_unit_test` explicitly asserts `cash_after_old_bug < 0` — it proves the old code was broken and documents the exact arithmetic. A developer who reverts the guard in montecarlo.rs would not be caught by these tests, but the test itself provides an auditable proof of the fix's correctness. The full-scale anchor (7dbf5628) changing under a revert would catch a revert at the §D6 anchor level.

**HANDOFF note to developer:** Add a unit test in `montecarlo.rs` that calls `run_path` with conditions designed to trigger solvency violation (e.g. many sell signals exhausting cash) and asserts equity never goes negative — this would provide the genuine RED-on-removal coverage that the current tests do not provide. This is a test completeness gap, not a Bug B fix correctness issue.
