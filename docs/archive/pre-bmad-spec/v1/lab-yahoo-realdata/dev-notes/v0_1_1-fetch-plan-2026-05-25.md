# v0.1.1 fetch + anchor-lock plan — operator hand-off

> **Audience**: operator (manual fetch step) → architect (M-T1 row stubs)
> → developer (anchor-lock wave). This is a hand-off doc, not a feature
> spec. The feature spec lives at
> [`spec/lab-yahoo-realdata/feature.md`](../feature.md); the architect
> will append a v0.1.1 section there in their pass.

## 1. TL;DR

1. **Operator runs the `fetch_yahoo_klines` CLI** (commands in § 2) to
   populate `data/yahoo/` with BTC-USD + ETH-USD + SPY daily bars across
   2024-01-01 → 2026-05-25, and turns on `.fetch_log.jsonl` logging.
2. **Developer wave then** registers a `btc-yahoo-2024-1d-sma-cross`
   scenario, runs it, anchors the report into
   [`evidence/anchors.toml`](../../../../evidence/anchors.toml), and lands H1 + H2 verdicts
   in a new dev-note. **Trigger**: cache populated, REVISION.toml present,
   `.fetch_log.jsonl` has ≥ 30 attempts across ≥ 3 sessions.
3. **What gates v0.1.1 ship**: H1 PASS (Yahoo vs Binance equity divergence
   < 30%) + H2 PASS (fetch success ≥ 95%) + new anchor row green on
   `cargo test --release -p backtest -- --ignored anchor`.

## 2. Operator fetch CLI — exact commands

The binary is gated behind `--features yahoo,yahoo-online` (declared in
`crates/data/Cargo.toml`). **Working directory MUST be the workspace
root** (`/Users/Vitaliy.Schreibmann/Projects/Privat/trading/trading`),
otherwise `--out data/yahoo` resolves to the wrong place — see Risk R4.

### Verbatim CLI surface (from `crates/data/src/bin/fetch_yahoo_klines.rs`)

Note: the arg is `--tickers` (plural, comma-separated) and `--out` (NOT
`--ticker` / `--cache-root` as you might guess from the H-pattern).

### 2.1 Dry-run smoke checks (no network, no disk writes)

Run these first to confirm CLI parsing + URL construction:

```bash
# Dry-run #1 — daily BTC-USD, full window
cargo run -p data --features yahoo,yahoo-online --bin fetch_yahoo_klines -- \
  --tickers BTC-USD \
  --interval 1d \
  --start 2024-01-01 \
  --end 2026-05-25 \
  --out data/yahoo \
  --dry-run

# Dry-run #2 — multi-ticker, daily
cargo run -p data --features yahoo,yahoo-online --bin fetch_yahoo_klines -- \
  --tickers BTC-USD,ETH-USD,SPY \
  --interval 1d \
  --start 2024-01-01 \
  --end 2026-05-25 \
  --out data/yahoo \
  --dry-run
```

Expected output: prints the query URL and expected bar count per ticker
(≈ 510 bars/ticker for the daily 2024-01-01 → 2026-05-25 window).

### 2.2 Real fetch — priority order

Run in this order (lowest-risk to highest-risk; first call validates
network reachability before you commit to multi-ticker fetches):

```bash
# Session A — H1 primary: BTC-USD daily, full window
cargo run -p data --features yahoo,yahoo-online --bin fetch_yahoo_klines -- \
  --tickers BTC-USD \
  --interval 1d \
  --start 2024-01-01 \
  --end 2026-05-25 \
  --out data/yahoo

# Session B — symmetry + H2 sampling: ETH-USD + SPY daily
cargo run -p data --features yahoo,yahoo-online --bin fetch_yahoo_klines -- \
  --tickers ETH-USD,SPY \
  --interval 1d \
  --start 2024-01-01 \
  --end 2026-05-25 \
  --out data/yahoo

# Session C — H2 fetch-rate sampling: re-fetch BTC-USD over a smaller
# window to pad the .fetch_log.jsonl attempt count (target ≥ 30 total).
cargo run -p data --features yahoo,yahoo-online --bin fetch_yahoo_klines -- \
  --tickers BTC-USD,ETH-USD,SPY \
  --interval 1d \
  --start 2025-01-01 \
  --end 2025-12-31 \
  --out data/yahoo
```

**Ticker rationale**:

- **BTC-USD** — primary H1 instrument; paired against the Binance
  BTCUSDT report anchored at `fc2e3b4a04055e60209fe85541173aa8883df226d2756352dfd101597168649c`.
- **ETH-USD** — symmetry / sanity (does the divergence story hold for a
  second crypto pair, or is BTC special?).
- **SPY** — non-crypto sample, exercises Yahoo's equity path (different
  Yahoo backend than crypto), gives H2 a heterogeneous attempt sample.

Why daily not minute: minute bars would balloon disk (~hundreds of MB
per ticker-year) and Yahoo throttles the minute endpoint harder. v0.1.1
locks H1 on daily; minute is a v0.1.2 follow-up.

### 2.3 Watch recipe for long-running fetches

If any session runs > 2 min (Session B + C likely will under
rate-limited backoff), open a second terminal and run:

```bash
watch -n 10 'find data/yahoo -name "*.parquet" -newer data/yahoo/REVISION.toml 2>/dev/null | wc -l; ls -lh data/yahoo/.fetch_log.jsonl 2>/dev/null'
```

Shows fresh parquet count + log file growth.

## 4. H1 evaluation plan — Yahoo vs Binance equity divergence

**Hypothesis**: `|equity_final(yahoo BTC-USD) - equity_final(binance BTCUSDT)|
/ equity_final(binance BTCUSDT) < 0.30` on the same SMA-cross strategy
over the overlapping window.

**Steps** (developer wave, after operator fetch is done):

1. **Baseline**: run the existing Binance-anchored scenario
   ```bash
   cargo run --release -p backtest --features realdata -- \
     --scenario btc-2023-1m-sma-cross
   ```
   and record `equity_final` from the printed report (or, better, the
   anchored report file body — `fc2e3b4a...` row in `spec/anchors.toml`).
   **Note**: that scenario uses Binance BTCUSDT 1m bars 2023; Yahoo
   doesn't cover the same window or cadence on the free tier.
2. **Comparable Yahoo run**: developer registers a new scenario
   `btc-yahoo-2024-1d-sma-cross` (see T-AR1) that calls the same
   `sma_composed_run::run` entry, but with a Yahoo daily 2024 bar
   source. Run it; record `equity_final`.
3. **Window alignment caveat**: 1m-2023-Binance and 1d-2024-Yahoo are
   **different windows + different cadences**, so the raw absolute
   numbers will diverge by construction. H1 needs a fair comparator —
   recommend the developer ALSO registers `btc-yahoo-2023-1d-sma-cross`
   for 2023 (Yahoo daily 2023) and compares against a NEW Binance daily
   2023 scenario (or accepts the cadence difference and documents it
   loudly). **Open question for architect — see § 9.**
4. **Verdict math**: compute the divergence ratio and emit it in the
   report under a `## H1 verdict` heading.

**Anchor question — recommendation: anchor-lock the Yahoo report.**
Rationale:

- Future Yahoo data revisions (Yahoo silently re-publishes historical
  bars when corporate actions land) would silently shift the equity
  curve and break H1 — anchor-locking gates that.
- The 34-anchor invariant is already non-negotiable per CLAUDE.md; one
  more row (35-anchor) costs ~5 min and stays cheap to maintain.
- Without anchor-locking, the H1 verdict is a one-shot diagnostic that
  can't regression-gate.

The new anchor lives in `spec/anchors.toml` under a new
`[[reports]]` row — see T-AR2.

## 5. H2 evaluation plan — fetch success rate

**Hypothesis**: `yahoo_finance_api 4.1.0` online fetch returns 2xx + parses
to a valid `LoadedBars` on ≥ 95% of attempts.

**Logging contract** (developer wave — T-AR4):

Extend `fetch_yahoo_klines` to append one JSONL row per HTTP attempt
to `data/yahoo/.fetch_log.jsonl`:

```json
{"ts_utc":"2026-05-25T14:32:11Z","ticker":"BTC-USD","interval":"1d","start_ms":1704067200000,"end_ms":1748131200000,"attempt":0,"outcome":"ok","bars_loaded":510,"latency_ms":823}
{"ts_utc":"2026-05-25T14:33:04Z","ticker":"ETH-USD","interval":"1d","start_ms":1704067200000,"end_ms":1748131200000,"attempt":0,"outcome":"rate_limited","retry_after_secs":5,"latency_ms":120}
{"ts_utc":"2026-05-25T14:33:10Z","ticker":"ETH-USD","interval":"1d","start_ms":1704067200000,"end_ms":1748131200000,"attempt":1,"outcome":"ok","bars_loaded":510,"latency_ms":901}
```

`outcome` enum: `ok`, `rate_limited`, `http_error`, `parse_error`,
`network_error`. **Definition of success for H2**: `outcome == "ok"`.

**Sampling design**:
- ≥ 30 attempts total (operator fetches Session A + B + C should
  comfortably exceed this — BTC-USD × 3 sessions + ETH-USD × 2 +
  SPY × 2 ≈ 7 base calls + retries).
- Spread across ≥ 3 distinct fetch sessions (Sessions A / B / C above).
- Across ≥ 3 distinct tickers (covered by BTC-USD / ETH-USD / SPY).

**Verdict math** (developer wave — T-AR5):

```text
success_rate = count(outcome == "ok") / count(*)
PASS if success_rate >= 0.95 AND count(*) >= 30 AND distinct(session_id) >= 3
```

Where `session_id` = bucket-by-day-+-hour of `ts_utc` (good-enough
proxy without instrumenting the CLI invocation explicitly).

H2 verdict lands in the same v0.1.1 dev-note as H1 (not anchored —
this is an operational metric, not a deterministic regression).

## 7. What blocks the dev wave

1. **Operator running the fetch CLI** — manual step, no CI substitute.
   Sessions A + B + C must complete successfully (any-error → bail).
2. **Network reachability of `query1.finance.yahoo.com`** — Yahoo
   unofficial API has no SLA. Operator should expect 1-2 retries per
   ticker under normal conditions; full failure means deferred wave.
3. **Disk space** — daily bars are tiny (~few MB per ticker-year), so
   the v0.1.1 fetch is ~50 MB max. Minute bars (out of scope) would
   need GB-scale planning.
4. **T-AR4 (log emission) lands before Session B** — otherwise the
   operator has to re-run sessions to populate the log. Mitigation:
   sequence T-AR4 to ship same-PR as the prep doc handoff.
